## P0（1 项）

### P0-1 fallback 管理记忆唯一副本存于向量库，rebuild 整库删除且永不重灌
- 位置：`backend/core/memory/memory_manager.py:438`（唯一落点 `store.add(user_id, "mem", ...)`，无任何 SQLite 落库）；`backend/core/memory/vector_store.py:277-292`（rebuild 逐 collection 删除后 `migrate()`）；`backend/core/memory/migration.py:96-138`（重灌源清单只有 long_memory/facts/triples/user_profile/important_dates/compact_summary 六个，**不含 mem**）
- 机理：Mem0 连续失败 3 次降级期间，`engine.on_message` 每轮仍写入 fallback 管理记忆，全部只存在于 Chroma。任何一次 rebuild（embedding 维度变化自动触发、加密迁移 `api/encryption.py:113`、关系包恢复 `relationship_export.py:527`）都会把这些记忆从唯一副本上物理删除，且无任何回填路径。
- 触发：Mem0 降级数日积累记忆后，换 `MEMORY_EMBED_MODEL` 或启用加密 → 降级期记忆永久丢失。
- 修复方向：fallback 记忆补一份 SQLite 权威表（或 migrate 纳入 mem 源），向量只做索引。

## P1（11 项）

### P1-1 run_command 危险命令黑名单可被 cmd `^` 转义混淆绕过
- 位置：`backend/tools/safety.py:66-131`（对原始字符串做正则匹配）+ `plugins/code_exec.py:208-228`（`shlex.split(posix=False)` 后 argv 直启）
- 机理：子代理实测 `check_command("cmd /c d^el /q x.txt")` 返回放行，而 `cmd /c e^cho caret-works` 实际输出 `caret-works`——cmd.exe 运行时把 `^` 脱掉还原成 `del`。`del /q`、`rm -rf` 等灾难命令写成 `cmd /c d^el ...` 即绕过「直接拒绝不弹确认」黑名单。`AGENT_CONFIRM_NO_CHANNEL=allow`/演示模式下确认层关闭时，黑名单是唯一防线。
- 修复方向：按 cmd 语义归一化后再匹配，或直接拒绝 `cmd /c` 自嵌套调用。

### P1-2 加密模式下记忆迁移用无 key 连接，rebuild 先删后灌失败可清空正常向量
- 位置：`backend/core/memory/migration.py:30、59`（`connect_database(...)` 未传 `encrypted_key`，对照 userdb `_ensure_connected` 与 maintenance/loop.py:315 均传）
- 机理：SQLCipher 文件无 key 首查抛 `file is not a database`；`_needs_migration` 捕获一切异常返回 False → 存量迁移永不跑。更糟：`rebuild_all` 先删光全部 collection 再调 `migrate()`，migrate 抛异常无补偿 → 加密态触发自动重建时连增量写入的正常向量也被清空。
- 修复方向：两处连接改走 `runtime.database_key_or_none()`；rebuild 先灌后删或失败补偿。

### P1-3 rebuild 删除 kb 知识库向量但 migrate 不重灌，知识库召回静默死亡
- 位置：`backend/core/memory/vector_store.py:277-283` + `backend/core/knowledge.py:187-190`（kb 向量唯一写入点在 ingest）、`:595`（recall 只查向量）
- 机理：`kb_chunks` 表有完整文本但全库没有从它重建向量的路径。rebuild（三个入口同 P0-1）后文档列表与 chunk_count 仍正常，`recall_knowledge` 永远返回空，重启不自愈。另：embedding 未就绪首日 ingest 被拒的 chunk 也无回填。
- 修复方向：migrate 增加从 kb_chunks 全量重灌 kb 分区。

### P1-4 离线补算 `_last_activity` naive/aware datetime 混用，有消息的用户必抛 TypeError
- 位置：`backend/core/offline_recap.py:39-57`（`max(moments)`；aware 的 `datetime.now().astimezone()` 与 messages.ts 的 naive 本地时间混比）
- 机理：子代理实际运行验证抛 `TypeError: can't compare offset-naive and offset-aware datetimes`。`maybe_generate` 不捕获 → 启动预生成只记日志、API 返回 500，D11 离线补算功能整体失效。测试 `test_offline_recap.py:126,130,169` 全部 patch 掉 `_last_activity`，恰好绕开真实实现所以全绿。
- 修复方向：统一时区基准（消息 ts 补 astimezone 或全程 naive 本地时间）。

### P1-5 五类关系事件的 L03 气质证据 / G01 初历登记被 `commit=False` 生产路径整体跳过
- 位置：`backend/core/relationship_events.py:110`（`if commit and event_id is not None:` 才执行 `record_evidence`/`note_event_for_first_occurrence`/`reevaluate_recent_facts_after_event`）；生产者 `activities.py:596-612`、`focus.py:178-192`、`cowriting.py:360-371`、`goals.py:306-316`、`colists.py:247-258` 全部传 `commit=False`

### 确认为真 bug（15 项）

#### 【P1】AgentPanel SSE 单流槽位：第二个任务的确认请求永久不可达（原前端可疑点，升级）
- 后端**没有**全局单任务闸：`_claim_running`（agent/session.py:330-341）只防同一任务双跑；`api_agent_run`（api/agent.py:210-227）不检查其他任务。两个任务可同时 running。

- 后果链：任务 B 的工具确认进入后端 `_pending` 后无人监听，`wait_for` 超时按拒绝处理（tools/confirm.py:78-80）→ B 被逐工具静默拒绝；关面板重开后 B 已 running，再点运行 409，且 `loadTask` 从不调 `startStream` → 无恢复手段。
