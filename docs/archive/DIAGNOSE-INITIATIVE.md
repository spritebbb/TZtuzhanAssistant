# 菟菚「主动对话」功能诊断报告

> 日期：2026-09-03
> 类型：只诊断、不改代码（用户已选「先诊断给结论，再决定改不改」）
> 症状：**乱主动 / 时机不对**（正常聊天时插话、刷屏、一天多次主动、频率/冷却像没生效）

---

## 一、先说结论（TL;DR）

菟菚的「先开口」其实有 **5 条互相独立、互不知情的触发路径**（见下表）。大多数「乱主动 / 插话 / 刷屏」观感不是某一段代码崩了，而是**这 5 条路径各管各的频率限制、互相不共享"当前用户是否正在聊天 / 今天是否已主动过"这把锁**，导致同一时段多条 bot 主动消息叠加出现。其中 **2 处是明确设计缺陷、可以直接算 bug**，其余是结构性隐患。

按「最可能就是你遇到的那个」排序：

| 优先级 | 根因 | 是否算 bug |
|--------|------|-----------|
| 🔴 高 | 归档建议会在**用户正聊天时**插话（不看"是否空闲"，只看消息数） | 是，明确设计缺陷 |
| 🔴 高 | 久别问候 + 主动引擎是两套独立系统，回 App 时会**叠加双主动** | 是，职责/去重缺失 |
| 🟡 中 | `poll_for`（主进程 30s 轮询）每轮都会真调 LLM，无并发占位 | 隐患，费资源+竞态 |
| 🟡 中 | "空闲 6h" 判定只看语义管线入库时间，问候/主动自己不推进时钟 | 结构性，多数情况是对的 |
| 🟢 低 | 全局冷却 15min 一刀切，和"每天 1 次"作用在不同层 | 设计取舍 |

## 二、5 条"菟菚先开口"路径全景

| # | 机制 | 触发点 | 频率/冷却限制 | 是否会插话正聊着的人 |
|---|------|--------|--------------|---------------------|
| A | **久别问候** greeting | `ChatView` onMounted + 每次切/重载会话 → `/api/greeting` | 距上次 ≥8h 才问候 | ❌ 基本不会 |
| B | **主动引擎** 后台 loop `_tick_once` | 后端启动常驻，每 5min 一轮；全局冷却 15min | 每用户每天 1 次、idle≥6h | ⚠️ 看时钟 |
| C | **主动** `poll_for`（Electron 主进程每 30s 轮询 + `/api/initiative`） | 主进程 `setInterval` 30s | 每用户每天 1 次、idle≥6h | ⚠️ 看时钟 |
| D | **SSE** `/api/initiative/stream` | 后台生成即实时推给开着的窗口 | 无独立限制（受 B 源头限制） | ❌ 只是通道 |
| E | **归档建议** `maybe_suggest_archive` | 挂在 `_tick_once` 内，全局冷却 15min | 会话 ≥40 条 + 当天 1 次 | ✅ **会！** |

---

## 三、🔴 根因一：归档建议不看用户忙不忙，正聊天时插话

**位置**：`backend/core/initiative.py` `_tick_once()` 第 159-165 行，调用 `maybe_suggest_archive()`。

**触发条件只有两条**：
1. 当前会话消息数 ≥ `_ARCHIVE_THRESHOLD`（40 条）；
2. 当天还没提醒过归档（`initiative:archive_suggest:今天` 无标记）。

**它完全不检查**：用户此刻是否正在聊天、离最后一条消息多久、用户是不是正看着屏幕。它的频率门（15min 全局冷却）是和"主动找人 B"**共享的同一把 `_last_global_run` 锁**，但"是否插话"没有任何门。

**后果**：你只要一个会话聊到 40+ 条（本地陪伴助手很容易到），哪怕你正一句接一句跟菟菚聊得热络，`_tick_once` 每 15 分钟一过就会**硬插一句"要不要归档这段对话？"**——这就是最典型的「明明在聊天却被菟菚打断」。

> 这其实是 V10（第四轮）把归档建议挂进 `_tick_once` 时留下的副作用：当时想让它"不受全局 cooldown 影响、每 5min 检查"，但检查逻辑里压根没有"用户正在聊天就闭嘴"的判定。

**佐证**：`_tick_once` 顶部的全局冷却 `_GLOBAL_COOLDOWN_SEC=900`（15min）return 0 时，**归档建议也被一起拦掉**；而归档建议自己的 `maybe_suggest_archive` 里也没有空闲判定——设计上它属于"提醒型主动"，跟"找人型主动"混用了同一套投递和频率通道，但缺了找人的"别打扰正在聊的人"这一条。

---

## 四、🔴 根因二：久别问候 A 与主动引擎 B/C 是两套系统，回 App 叠加双主动

**两套系统各自独立**：

| | A 久别问候 greeting | B/C 主动找人 initiative |
|---|---|---|
| 判断"多久没来"用 | `web_last_seen`（kv，greeting 自己维护） | `db.last_message_ts`（userdb 语义管线消息） |
| 空闲阈值 | 8h | 6h |
| 每天上限 | **无**（靠 8h 间隔天然限制） | 每天 1 次 |
| 谁触发 | 打开窗口 / 切会话（拉模式） | 后台 loop / 30s 轮询 + SSE（推/拉） |
| 是否写同一个"今天已主动"标记 | ❌ 不写 | ✅ 写 `_proactive_key` |

**后果**：用户久别（≥8h）回到 App → onMounted 触发 A 弹一句问候。**同一时刻**，若从"最后一条语义入库消息"算起已 idle ≥6h，后台 loop B 或主进程轮询 C 会**再主动联系一次**。两条路径互不认账、不查对方的"今天已主动"标记，短时间连弹两句「菟菚先开口」，观感就是"话痨 / 刷屏 / 时机怪"。

**且两边判"空闲"的时钟不同源**：greeting 用自己维护的 `web_last_seen`，initiative 用语义管线的入库时间。二者可能一个判"久别"、另一个判"还在聊"，完全错位。

---

## 五、🟡 根因三：`poll_for` 每 30s 真调 LLM、无并发占位（费资源 + 竞态）

**位置**：`backend/core/initiative.py` `poll_for()`（第 307-330 行），被两个入口高频调用：
1. Electron 主进程 `pollInitiative()`：`setInterval` **每 30s** 调 `/api/initiative`；
2. `/api/initiative` 端点：队列空时兜底调 `poll_for`。

**`poll_for` 内部每次都会**：
- 读库判 stage / 今天是否主动过 / 是否 idle≥6h；
- 三项都放行时就 `generate_proactive_message()` **真调一次 LLM**（DeepSeek）。

**问题**：只要"今天还没主动过 + idle 达标"这个窗口一直开着，主进程每 30s 就可能发起一次 LLM 生成。虽有"每天 1 次"兜底（`_mark_proactive` 只在生成成功后才置位），但：
- 生成是**异步耗时**操作，在这几十秒里另一路径（后台 loop）可能也生成了另一条 → 生成两遍、取其一，浪费一次；
- 生成**失败**（LLM 抖动）时不置位 `_mark_proactive`，下一轮 30s 后又重试 → 若服务连续异常，等于每 30s 撞一次 LLM，直到成功。

这解释了"感觉它老在折腾 / 资源被偷偷占用"类观感。

## 六、🟡 根因四：空闲时钟只认语义管线，主动/问候不推进自己

**佐证链路**（已核实代码）：
- 用户消息**总是** `db.add_message(user_id,"user",...)`（`pipeline.py:518`），会推进 `db.last_message_ts`；
- assistant 回复只在生成成功分支补存（`pipeline.py:1171`）；
- 问候（`greeting.py`）、主动消息（`store.append_proactive_message`）都**只写会话 store，不写 userdb messages** → 不推进 `db.last_message_ts`。

**含义**：initiative 的"空闲 6h"是从**用户最近一句真实聊天**算起的，问候/主动自己不重置它。这其实**多数时候是正确设计**（菟菚只该在用户真停聊 6h 后才主动）。只有当：
- 用户在另一个不进语义管线的通道聊（如 agent 任务面板 `assistant-main` 身份/旧 `session_current` 身份残留），或
- 用户只是挂着窗口没发消息

时，会出现时钟与实际"人还在不在用"不一致。属结构性隐患，非即时 bug。

---

## 七、🟢 根因五（取舍）：全局冷却 15min 与"每天 1 次"作用在不同层

- `_GLOBAL_COOLDOWN_SEC=900` 管的是"每次检查轮次之间至少隔 15min"，防止后台 loop 密集生成；
- 但 **`poll_for`（拉模式）根本不吃这个冷却**——它只看"每天 1 次"。

于是同样"找人多主动"这件事，推模式（loop）和拉模式（poll）是**两套限流**。要做到"真的一天一次、且不在聊天时插话"，需要一个统一的、会话级的"今天已主动 + 当前不在忙"的信号，当前没有。

## 八、修复方向（供确认，本次未动代码）

按 ROI 从高到低，候选改动（都低风险、可单点）：

1. **归档建议加"正在聊天就别插"**（根因一，最值得先修）
   在 `maybe_suggest_archive` 里补"距最后一条消息 < N 小时就闭嘴"判定（对齐 `_IDLE_HOURS` 或更短，如 30min/1h），只有真的 idle 才提醒归档。或把归档建议挪出"正聊"的判定口。
   → 直接消除"正聊天被插一句归档"。

2. **问候与主动引擎共享"今天已主动"去重**（根因二）
   让 A（greeting）与 B/C（initiative）读写同一个每日标记（或至少让 initiative 在 A 刚问候过、时钟很短时不叠加）。两套"先开口"归一到一个调度。
   → 消除"回 App 双主动"。

3. **`poll_for` 加生成中占位 + 尽量少真调 LLM**（根因三）
   参考 greeting 的 `_GREET_PENDING_KEY` 占位模式：生成中置 kv 标记，避免 loop 与 poll 并发双生成；把主进程 30s 轮询改成只在"上次生成已结束且未成功"时再试。
   → 省 LLM 调用、消竞态。

4. **（可选）统一"主动"总开关 + 频次配置外置**
   把 5 条路径的阈值（idle 时、每天次数、是否允许归档插话）收敛到 config，便于调参，而非散落常量。
