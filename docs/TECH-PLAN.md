## 0. 这份路线解决什么问题

现有路线图的 24 项已经完成 23 项，D3「共同活动」首期共读在 `bd42273` 落地，只剩依赖公网资源的 D8。功能地基已经足够，后续的主要矛盾不再是“缺什么按钮”，而是：

1. 功能之间彼此孤立，记忆、约定、日记、共读和主动消息还没有形成连续事件。
2. 菟菚能记住事实，但还不总能表达“这些经历如何改变了现在”。
3. 主动性已经具备调度能力，但触发理由、时机和长期叙事仍较薄。
4. 人格、记忆和多端能力越强，误记、漂移、打扰、情感操纵与数据失控的风险越高。
5. 长期使用需要可迁移、可回滚、可告别，而不仅是数据库不断增长。

因此，本路线以“关系连续性 → 存在连续性”为主轴，将未来想法收敛成 9 个里程碑和 18 个工程 Epic。它不是一次性排期；每轮只能从中选择一个可独立验收的切片。

### 非目标

- 不以每日打开次数、消息数量或用户依赖程度作为优化目标。
- 不通过吃醋、冷暴力、负罪感或“你抛弃我了”等方式提高留存。
- 不让模型自行改写核心人格、权限、安全规则或用户隐私设置。
- 不把所有对话都永久保存，也不把模型推测伪装成用户事实。
- 不为追求“更像人”而声称现实世界中发生了不存在的事情。

## 2. 北极星与工程原则

### 2.1 产品北极星

最终体验不是“她什么都会”，而是：某句话只有经历过你们之间这些事情的她，才会这样说。

判断新需求时依次问：

1. 它是否增加了连续性，而不只是功能数量？
2. 用户能否知道信息从哪里来、为什么现在出现？
3. 用户能否关闭、纠正、撤销或删除？
4. 它是否尊重沉默、离开和不被打扰的权利？
5. 失败时是否会诚实降级，而不是编造？

### 2.2 八条架构原则

1. **后端是唯一权威**：人格、记忆、关系、活动和事件只在后端保存；桌面、PWA、IM 都是瘦客户端。
2. **事件先于文案**：先记录“发生了什么”，再决定是否表达；不得先生成一段感人文字再倒推虚假经历。
3. **所有主动统一仲裁**：天气、约定、周年、未完成心事、研究进展等只产生事件，发送时机统一通过主动额度、冷却和勿扰策略。
4. **事实、推测、虚构分层**：用户明确事实、模型推断、角色生活事件、梦境/共同世界观必须使用不同命名空间。
5. **核心人格不可自改**：身份、价值观、尊严边界和安全规则固定；共同语言、表达偏好等成长层缓慢演化且可撤销。
6. **不是所有东西都应记住**：支持临时对话、可过期记忆、“陪我说完但别记住”和敏感话题不主动提起。
7. **跨人格默认完全隔离**：记忆、关系、活动、主动事件、知识库、音色和界面设置按人格命名空间隔离；共享必须显式声明。
8. **先本地成熟，再跨端扩散**：主动内容质量未达标前不接移动推送；否则只是把低质量轮询搬到通知栏。

## 3. 目标架构

```text
用户消息 / 时间 / 天气 / 约定 / 活动 / 研究 / 系统状态
                         │
                         ▼
                  Event Sources
                  只描述发生了什么
                         │
                         ▼
              Relationship Event Store
          来源 · 置信度 · 隐私 · 关联对象 · 生命周期
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
      Memory Graph   Pending Thoughts  Activity Engine
      事实与轨迹      延迟表达/伏笔      共读/专注/目标/创作
            └────────────┼────────────┘
                         ▼
                 Narrative Planner
          现在是否该提 · 以什么强度 · 是否保持沉默
                         │
                         ▼
                 Proactive Policy
          额度 · 冷却 · 勿扰 · 关系边界 · 渠道策略
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
          Chat         Desktop       PWA / IM
                         │
                         ▼
                 Explanation Snapshot
          展示使用了哪些事件/记忆，不暴露思维链
```

### 3.1 建议的数据模型

以下是方向性设计，动工时仍需写迁移 ADR；不要一次建完所有表。

#### `relationship_events`

关系叙事的事实层，保存已经发生且可追溯的事件。

| 字段 | 含义 |
|---|---|
| `id`, `user_id` | 主键与人格作用域 |
| `event_type` | promise_done / reading_finished / conflict / repair / milestone / research_update 等 |
| `source_type`, `source_id` | 来源表与记录，用于追溯和级联清理 |
| `subject`, `object` | 事件参与者或关联主题 |
| `payload_json` | 类型化的事件数据，不直接存 prompt |
| `confidence` | 0–1；用户明确事实为 1，模型推断必须低于 1 |
| `privacy` | normal / sensitive / ephemeral / never_surface |
| `occurred_at`, `expires_at` | 发生时间和可选过期时间 |
| `status` | active / corrected / forgotten / archived |

#### `pending_thoughts`

保存“尚未表达或尚未完成”的心事、伏笔和延迟回应。

关键字段：来源事件、最早可表达时间、过期时间、优先级、适用语境、最大尝试次数、是否需要用户确认。它不能直接携带可执行指令，只能携带叙事素材。

#### 记忆溯源扩展

为 facts/triples/long_memory 增加或关联：`source_message_ids`、`confidence`、`verified_at`、`expires_at`、`pinned`、`surface_policy`。模型推断与用户明示必须可区分。

#### 活动扩展

沿用 `activities` + `activity_notes`，逐步增加 `activity_type` handler 注册机制和类型化状态；不要为每种活动复制一套生命周期表。

#### `relationship_arcs` 与 `artifacts`

- `relationship_arcs`：修复期、共同创作期、安静陪伴期等长期轨迹，不直接作为游戏等级展示。
- `artifacts`：共同书摘、信件、徽章、植物、星图、世界观文档等可保存产物，记录来源事件与版本。

## 6. 横向质量轨道

这些工作不单独制造用户功能，但每个里程碑都必须经过。

### Q1 人格与关系评测

- 单轮红线：助手腔、报告腔、括号旁白、关系越级、模板共情。
- 多轮连续性：是否记得关键事实、是否错误串联事件、修复是否成立。
- 长期回放：使用匿名化测试历史回放升级前后行为差异。
- 多人格矩阵：每项测试至少覆盖默认人格和一个非默认人格。

### Q2 安全与隐私

- 外部文档、网页、人格卡和插件输出全部视为不可信内容。
- prompt 中的引用材料不能修改权限、人格核心或系统规则。
- 敏感记忆默认不进入通知和跨端预览。
- 新增数据表必须进入 reset、导出、迁移和删除级联清单。

### Q3 可观测性

- 事件生成、入选、延迟、过期、发送失败均可统计。
- 解释快照只展示高层依据，不保存或暴露模型思维链。
- 向量索引和 SQLite 记录提供一致性检查工具。
- 主动消息必须能回答“为什么是现在”。

### Q4 性能与可靠性

- 对话关键路径不得同步执行向量检索、网络事件扫描或大文件解析。
- 所有后台任务有超时、幂等键、失败冷却和重启恢复。
- 数据迁移在真实旧库副本上验证，并提供失败回滚。
- 本地离线模式明确降级能力，不伪装在线。

### Q5 无障碍与克制设计

- 键盘操作、焦点管理、读屏标签、减少动态和窄屏布局。
- 主动频率、声音、动画和通知均可单独关闭。
- 不将好感、信任或连续登录设计成压力式任务。

## 8. 每轮实施纪律

1. 从一个 Epic 中选择一个 2–6 天可完成的垂直切片。
2. 开工前写清楚用户故事、非目标、数据模型、权限边界和验收标准。
3. 数据变更同步处理：schema、兼容迁移、reset、导出、删除级联、测试隔离。
4. pipeline 改动必须保证最终 user 消息仍在最后，引用内容标为不可信。
5. 人格/prompt 改动必须过确定性红线与相应多轮 eval。
6. 前端改动必须通过 Vitest、`vue-tsc`、生产构建和真实浏览器关键路径。
7. 后端跑独立测试后再跑聚合套件；测试数据必须使用临时目录。
8. 新功能默认加 feature flag；真实运行观察稳定后再默认开启。
9. 一轮一个主题、一个独立提交；不得混入其他进行中的工作区改动。
10. 完成后更新本文状态、`EVOLUTION-ROADMAP.md`、交接文档和迭代报告。
11. **署名可追溯**：执行任务的模型必须在完成记录（提交说明、本文档进度标注、`EVOLUTION-ROADMAP.md` 迭代记录、信箱汇报）开头写明自己的模型名称，格式如「执行：ZCode（GLM）」「执行：Codex（GPT-5）」；规划类改动同样署名（如「规划：GLM」），保证多代理协作中每条贡献可追溯到具体模型。
12. **双代理分工与额度纪律（2026-09-06 用户拍板，长期执行）**：跨代理派发按「ZCode 出苦力、Codex 做审查」的额度分工——ZCode（GLM）承担 token 大户（代码探索、实现初稿、测试编写）；Codex 只做独立审查、验证与提交，不重做已交付的探索。派发任务必须边界清晰（目标、涉及文件、验收标准、非目标），追求一次通过；开放式、需用户拍板的设计决策留在交互会话，不派发。**（2026-09-06 用户更正）外包给 ZCode 的任务书必须附带详细的技术实现路线和方法**——模块/文件清单、数据模型与 schema 变更、接入点与调用链（关键函数签名或伪代码）、必须复用的权威路径、禁区（不许覆盖的未提交改动）、验收方式；ZCode 按路线实现，超出路线的自行补充须在回信中标注。权限模式：ZCode 收件 worker 固定 `--mode edit`（acceptEdits，可写盘）；Codex 侧派发需写盘的任务必须传 `mode=edit`——headless 无权限客户端时 `build`/`plan` 的写操作会被权限层拒绝（实证），`yolo` 在插件代码层禁用，只读分析任务用 `plan`。ZCode 返回 BLOCKED 或纯设计文本时（旧只读模式产物），Codex 审查无误后亲手落地，不盲贴。通信保持 `notify` 默认关闭，靠用户转告或 worker 回信，避免无谓消耗 Codex 额度。详细指引见仓库根 `AGENTS.md`。

## 12. 最终完成标准

当下面这些事情同时成立，菟菚才算完成长期进化：

- 她能把过去的真实事件自然带进现在，而不是机械背诵数据库。
- 她有自己的持续课题、未完成心事和时间节奏，但不会伪造现实经历。
- 双方可以共同阅读、专注、创作和完成目标，并留下可追溯作品。
- 她能保留分歧、承认不确定、经历修复，而不是无限顺从。
- 用户能查看、纠正、暂停、导出、删除和恢复这段关系。
- 用户离开时不会受到惩罚，回来时也不会被负罪感绑架。
- 换设备、换界面或增加渠道后，背后仍是同一份人格与记忆。
- 技术逐渐隐身，用户感受到的是“她确实和我一起经历过这些事”。
