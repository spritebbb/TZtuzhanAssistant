# 代码审查标准与流程（Code Review Standard & Process）

> 适用项目：菟菚桌面助手（TZtuzhanAssistant）
> 制定：代码审查专家 · 火眼眼
> 版本：v1.0 · 2026-09-03

---

## 一、为什么要建立审查机制

项目已从单文件 `assistant.py`（67KB）重构为分层架构（backend 86 个 Python 文件、约 1.4 万行 + 前端 Vue3/Electron），并接入了**本机高危能力**：任意 Python 代码执行、系统命令、文件读写、进程操控、剪贴板、截图、外部 Agent（Codex/DSH）派发。这类能力一旦有 bug，不是"崩溃"这么简单，而是**数据损坏、越权、甚至本机沦陷**。

代码质量参差不齐的根源通常有三：**缺统一标准、缺流程约束、缺自动化兜底**。本文档一次补齐。

---

## 二、审查的四条核心价值观

1. **正确性优先** —— 先问"它对不对"，再问"它好不好"。
2. **安全是底线** —— 涉及本机能力的代码，安全审查不通过一律不合并。
3. **可维护性看长期** —— 代码写一次、读百次，6 个月后还有人能看懂才算合格。
4. **审查是教学，不是找茬** —— 每条意见都要说清"为什么"和"怎么改"。

---

## 三、问题分级标准（统一口径）

| 级别 | 标记 | 定义 | 处理要求 |
|------|------|------|----------|
| P0 崩溃级 | 🔴 | 崩溃 / 数据损坏 / 安全漏洞 / 死锁 | **立即修，阻断合并** |
| P1 高 | 🟠 | 功能正确性 / 数据一致性隐患 / 高危边界 | 本迭代尽快修 |
| P2 中 | 🟡 | 健壮性 / 性能 / 代码异味 / 缺测试 | 择机修，登记 backlog |
| P3 低 | 🔵 | 死代码 / 风格 / 文档 / 潜在理论隐患 | 可忽略或顺手改 |

**判定口诀**：会不会出事（P0）→ 会不会错（P1）→ 会不会烂（P2）→ 会不会乱（P3）。

## 四、审查检查清单（Checklist）

### 4.1 安全（🔴 重点，本机能力项目必查）

- [ ] **SQL 注入**：所有 SQL 是否参数化（`?` 占位符），有无 f-string 拼 SQL？
- [ ] **命令注入**：`subprocess` 是否用列表参数（`shell=False`），有无 `shell=True` / `cmd /c` 夹带？
- [ ] **沙箱逃逸**：代码执行（exec/eval）有无黑名单/白名单？反射链（`__class__`/`__mro__`/`__globals__`）是否封死？字符串拼接/编码混淆能否绕过 AST 静态扫描？
- [ ] **路径穿越**：文件操作是否经过 `resolve()` + 白名单根目录校验，`..` 逃逸是否拦截？
- [ ] **SSRF**：外部 URL 访问是否校验 scheme、拒绝内网/回环地址、DNS 重绑定是否复检？
- [ ] **鉴权**：写端点 / 远程端点是否有来源 IP 校验 + token？是否信任可伪造头（X-Forwarded-For）？
- [ ] **敏感信息**：密钥/token/password 是否脱敏后才进日志、确认框、审计记录？
- [ ] **危险操作确认**：写/命令/外部类工具是否走确认钩子，钩子异常时是否**默认拒绝**（而非放行）？

### 4.2 正确性（🔴/🟠）

- [ ] 空值 / 边界（空串、None、超长输入、0/负数、越界索引）是否处理？
- [ ] 异常路径是否被吞掉关键信息？`except Exception: pass` 是否掩盖了真实 bug？
- [ ] 资源是否泄漏：文件句柄、子进程、数据库连接、临时文件是否 finally 释放？
- [ ] 异步正确性：`await` 是否漏写？`to_thread` 是否丢失 contextvar？超时是否真的 kill 子进程？
- [ ] 幂等性：重复调用是否安全（启动初始化、迁移 ALTER、去重逻辑）？

### 4.3 并发 / 数据一致性（🟠）

- [ ] 共享状态是否有锁？锁的粒度与作用域是否正确（`asyncio.Lock` vs `threading.Lock` vs `RLock`）？
- [ ] 跨线程 / 跨进程访问同一资源（SQLite 连接、文件）是否会撞锁 / 竞态？
- [ ] 数据库写是否成对 commit，失败时是否会留下半更新状态？

### 4.4 性能（🟡）

- [ ] N+1 查询、循环内建连接、全表扫描（大表无 LIMIT）？
- [ ] 超长输出 / 大文件是否有截断，避免撑爆上下文或内存？

### 4.5 可维护性（🟡/🔵）

- [ ] 命名是否清晰？有无误导性变量名？
- [ ] 死代码 / 无用 import / 遗留的旧架构代码（如多会话 CRUD）是否清理？
- [ ] 关键逻辑有无注释说明"为什么"，而非复述"做什么"？
- [ ] 重复代码是否该抽公共函数？

### 4.6 测试（🟡）

- [ ] 高危路径（沙箱逃逸、路径穿越、SSRF、确认拒绝）有无针对性测试？
- [ ] 边界条件有无用例？
- [ ] 改动是否破坏现有测试？

## 五、审查流程（六步走）

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 1.范围确认 │ → │ 2.逐文件读 │ → │ 3.分级标注 │ → │ 4.验证复现 │ → │ 5.输出报告 │ → │ 6.跟踪闭环 │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 第 1 步：范围确认
- 明确审查对象（哪个模块 / 哪次提交 / 哪条链路）。
- 优先审**高危模块**：`plugins/code_exec.py`、`plugins/system.py`、`plugins/external.py`、`backend/tools/safety.py`、`backend/tools/confirm.py`、`backend/api/*`（写端点）。

### 第 2 步：逐文件通读
- 按调用链读，不孤立读单文件。
- 重点看：输入边界 → 校验 → 执行 → 持久化 → 异常 → 资源释放 全链路。

### 第 3 步：分级标注
- 每条问题按第四节分级，标注 `文件:行号` + 代码片段 + 原因 + 建议。

### 第 4 步：验证复现（关键，防止"我以为"）
- 安全类、正确类问题**必须实际跑一遍复现**（写最小复现脚本），确认不是误报。
- 拿不准的边界，宁可标"待确认"也不要妄下结论。

### 第 5 步：输出报告
- 结论速览表（P0/P1/P2/P3 数量）→ 分级详述 → 确认"非 bug"清单 → 修复优先级。
- 报告落盘 `docs/CODE-REVIEW-V{n}.md`，编号递增。

### 第 6 步：跟踪闭环
- P0 修复后必须回归验证。
- P1/P2 登记 TODO，明确负责人和迭代。
- 修复结果回写到报告（标注"已修复/已确认"）。

## 六、自动化兜底（把人能漏的交给机器）

| 手段 | 工具 | 拦截什么 |
|------|------|----------|
| 静态检查 | ruff / flake8 | 未用 import、未定义变量、死代码 |
| 类型检查 | mypy / pyright | 类型错误、None 解引用 |
| 安全扫描 | bandit | SQL 注入、shell=True、eval、弱随机 |
| 单测 | pytest（已有 30 个测试文件） | 回归、边界 |
| 高危专项测试 | 手工脚本 | 沙箱逃逸、路径穿越、SSRF（机器测不全，需人工复现） |

**建议最小落地**：`requirements.txt` 加 `ruff` + `bandit`，CI 或提交前跑 `ruff check` + `bandit -r backend plugins`，先拦最浅层的（未用 import、`shell=True`、裸 `exec`）。

## 七、本机能力项目的三条铁律（本项目特有）

1. **确认钩子默认拒绝**：任何 write/run/external 类工具，在确认通道异常、超时、无前端时，**一律按拒绝处理**，绝不允许"未经确认执行"。
2. **沙箱不可自欺**：代码执行沙箱用黑名单只能防误操作，不能防恶意。真正的高危能力（run_python 等同本机权限）必须在确认文案里**如实告知用户风险**，而非暗示"已安全隔离"。
3. **审计不可省略**：所有工具调用必须落 `tool_log.jsonl`，敏感参数脱敏，失败也不干扰主流程，但**不能因为"审计失败静默"而放弃审计**。
