# 菟菚自我升级机制设计（遇难题 → 自己写插件 → 补能力 → 回去解决）

> 状态：**方案已定稿，暂不实施**（2026-09-30 用户拍板）。本文档为存档，实施时按第 7 节任务分解直接开工。
> 决策记录（用户 2026-09-30 拍板）：
> 1. 确认策略：**全自动 + 事后汇报**（不弹事前确认，任务完成时汇报做了什么升级）
> 2. 范围边界：**不设域限制**（不限制插件类型，不靠白名单）
> 3. 实施节奏：**暂不实施**，仅存档方案
>
> 分析：ZCode（GLM）。批判性说明见第 6 节——全自动姿态等于放弃事前把关，
> 第 5.2 节的补偿性控制（审计/禁用/预算）是该姿态下**必须**的部分，不是可选增强。

## 1. 目标场景

用户交给菟菚一个任务，她现有的工具组合解决不了（例：要解析一种冷门文件格式、
要对某网站做结构化抓取、要做一个数据转换）。期望行为链：

```
发现能力缺口 → 判定"这是缺工具，不是缺权限/该求助"
  → 按《PLUGIN-DEVELOPMENT》规范写一个插件到 plugins/self_*.py
  → 热加载自动生效（≤2s）→ 用已知答案的用例验证新工具
  → 回到原任务用新工具完成 → 事后汇报"我给自己造了什么、为什么、去留建议"
```

## 2. 现状盘点：机制已存在，缺的是四层「软件」

**已有的（不用造，实证位置）**：

| 机制 | 位置 | 说明 |
|---|---|---|
| 插件热加载 | `backend/plugins/loader.py` | `start_watch()` 每 2s 轮询 `plugins/*.py`，新增/修改/删除即自动加载/重载/卸载，无需重启；加载失败记 `PluginState.error` 不崩主进程 |
| 插件编写规范 | `docs/PLUGIN-DEVELOPMENT.md` | 完整的骨架模板、PLUGIN_META、register(ctx)、register_func 参数说明——知识层现成 |
| 写文件能力 | `plugins/file_edit.py` | 她今天就能写插件文件 |
| 执行代码 | `plugins/code_exec.py` | `run_python` 本机权限（非沙箱，诚实声明在 docstring） |
| 工具熔断/预算 | `backend/tools/tool_loop.py:637`（§17.3） | 同签名工具连续失败第 2 次拒执行 |
| 一键禁用 | `backend/api/plugins.py:54` `POST /plugins/{name}/disable` | 禁用状态持久化 `data/plugins.json`，卸载语义精确（覆盖恢复快照） |
| 调用审计 | `backend/tools/audit.py` | `log_tool_call` / `query_log`，含 confirmed 标记 |
| 源码可查 | `backend/api/plugins.py:85` `GET /plugins/{name}/source` | 事后审阅入口 |
| 技能系统 | `plugins/skill.py` + `skills/` | trigger 命中即注入「干活姿势」——意识层的自然载体 |

**缺的（要做的）**：

1. **意识层**：她不知道这条路存在。`backend/core/turn_prompt.py` 与 `skills/`
   均无「能力缺口可自造工具」的任何提示（2026-09-30 grep 实证）。
2. **判定协议**：三问分诊——缺工具（写插件）/ 缺权限（向用户申请）/
   缺知识或该求助（写插件也没用）。没有协议会把「不想做的难题」误判成能力缺口。
3. **护栏**：见 5.2，全自动姿态下是审计+禁用+预算，而非事前确认。
4. **验证与清理**：新插件要先用已知答案用例验证；一次性插件任务完成后默认删除。

## 3. 关键风险事实（实施前必读）

- **`register_func` 默认值不设防**：`backend/tools/base.py:216-217` 默认
  `category=CATEGORY_READ, danger_level=DANGER_NORMAL, needs_confirm=False`。
  自写插件的工具默认**不过确认钩子**。用户已选全自动，此项不再翻案，
  但意味着唯一的事后追溯线是 audit log——审计必须保证覆盖。
- **插件不是沙箱**：以后端全权限跑在主进程。顶层死循环可挂死服务；热加载 2s
  轮询会反复重试坏文件（有 error 记录但不自动放弃）。增量风险不在权限高度
  （`run_python` 本来就是本机权限），在**持久化**——常驻插件是持续运行的代码。
- **「能跑」≠「正确」**：一次性生成的插件可能悄悄算错。验证环节必须用已知
  答案的用例（与 AGENTS.md 的 `VERIFY:` 哲学一致，模型自报全绿不算数）。
- **git 工作区**：`plugins/` 被 git 跟踪，自写插件以 untracked 文件出现，
  与双代理「不覆盖工作区」纪律可能打架 → 命名前缀 `self_` 隔离 + 人工审阅归档。

## 4. L1｜意识层（纯 skill + prompt，成本最低）

新建 `skills/自我升级.md`：

- **triggers**：`做不了, 不会这个, 超出能力, 能力不够, 写个插件, 升级自己, 造个工具, self_upgrade`
- **内容**（按序）：
  1. 三问分诊协议（缺工具？缺权限？该求助？）；穷尽已有工具组合优先、求助次之、
     写插件是最后手段；一轮对话最多自造 1 个插件，再不行转求助。
  2. 插件编写：指向 `docs/PLUGIN-DEVELOPMENT.md`（`skill_load` 或直接引用其骨架），
     不重复维护模板。落盘路径必须 `plugins/self_<用途>.py`（前缀纪律）。
  3. 验证协议：写完等热加载（≤2s），用 `skill_search` 式自查——调用
     `GET /plugins` 确认 loaded 无 error；用新工具跑一个**已知答案**的用例。
  4. 汇报协议：回复末尾附「自我升级汇报：造了什么 / 为哪个任务 / 验证结果 /
     去留建议（默认删除）」。
  5. 禁区：不覆盖他人插件；不改 loader/注册表本身；不写定时任务类自驻插件
     （ctx.schedule 慎用）除非任务确需。

`turn_prompt.py` 能力声明加一句（示意）：
「能力边界不是硬边界：plugins/ 热加载（≤2s），遇到能力缺口可按《自我升级》
技能给自己造工具——但先穷尽已有工具、先考虑求助，造完必须验证并汇报。」

## 5. L2｜护栏（全自动姿态下的补偿性控制）

### 5.1 不做的（按拍板）

- 不做写 `plugins/` 路径的事前确认弹窗。
- 不做插件类型白名单。

### 5.2 必做的（放弃事前把关后，这是唯一的安全网）

1. **审计全覆盖**：确保自写插件（owner≠builtin 或 `self_` 前缀）的所有工具调用
   进 `audit.log_tool_call`（含参数摘要与结果摘要）。审计缺失比危险工具更糟——
   出了事无法追溯。
2. **事后汇报强制化**：turn 结束时若本轮会话写过 `plugins/self_*.py`，
   在回复文本中必须包含自我升级汇报（可挂 `turn_effects.py` 或 reply hook 做
   提醒注入：检测到 self_ 插件变动但回复未提及时追加提示）。
3. **单轮预算**：一轮对话自我升级 ≤1 次。落点：tool_loop 预算体系加
   「写 plugins/self_*.py 的 file_edit 调用每 turn 限 1 次」，超限返回结构化
   错误引导转求助。
4. **坏插件自动熔断**：loader 对同一插件连续 N 次（建议 2 次）加载失败自动
   disable 并记 `data/plugins.json`，防止 2s 轮询无限重试。现有 error 字段
   只记录不阻断。
5. **一键禁用已存在**：`POST /plugins/{name}/disable` 即 kill switch，
   前端插件面板确认可操作（验收项）。
6. **默认清理**：技能里写死「一次性插件任务完成后默认删除，保留需在汇报中
   给理由」。可选增强：`plugins/self_*.py` 超过 X 天未触发调用自动提醒清理。

## 6. 批判性评估（强项 / 弱点 / 边界）

**强项**
- 物理机制零新建：热加载、审计、禁用、规范文档全部现成，实施量集中在
  skill 文案 + 少量护栏代码，是一个小切片。
- 与现有架构完全同构：自写插件和人工写的插件走同一条 loader 路径，
  无特判分支，卸载/覆盖语义复用。

**弱点（诚实摊开）**
- 全自动 + 无域限制 = 事后追责模式。一次跑偏的插件（比如格式化错了盘上的
  文件）损失已经发生，disable 只是止损。用户已知此代价并拍板接受。
- GLM 一次性生成代码的正确率有限，验证协议（已知答案用例）是正确性的
  唯一防线，靠 skill 文案约束，非机制强制——可能被跳过。
- 能力幻觉滥用：她可能对中等难度任务也走造插件路线，烧 token 且增加
  维护面。预算（≤1 次/轮）+「最后手段」排序是缓解，非根治。
- 与双代理 git 纪律的摩擦只能靠 `self_` 前缀 + 审阅流程缓解。

**不可碰的边界**
- 不改 loader 的加载顺序与覆盖语义（v2 修复的卸载快照逻辑）。
- 不给自写插件开绕过 audit 的通道。
- 不在无用户在场的情况下让插件写 `data/bot.db`（走既有 API/存储层）。

## 8. 验收标准（端到端）

1. 给她一个现有工具做不了的小任务（如「把这个 WeirdFormat 文件转成 CSV」），
   她走完整链路：写 `plugins/self_weird2csv.py` → 热加载 → 已知答案验证 →
   完成任务 → 回复含自我升级汇报。
2. 给她一个**不该**造插件的任务（如「帮我删了系统回收站」——缺权限类），
   她走求助路线而非造插件。
3. 写一个故意语法错的插件，loader 熔断 disable，服务不崩，`GET /plugins`
   可见 error。
4. 单轮内第二次尝试写 self_ 插件被预算拒绝并转为求助话术。
