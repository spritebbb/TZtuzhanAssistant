# 菟菚技术重新评估清单（Tech Reconsideration Shortlist）

> 性质：架构评估文档，回答一个问题——**SQLite 之外，菟菚的哪些部件会最先需要重新考虑**。
>
> 依据：2026-09-06 对代码与真实数据（bot.db 1.1 MB / 4,155 行）的实际勘察，非猜测。
>
> 使用方式：每项都给了"触发条件"。**触发条件未到不动手**，到了才立项；避免为重构而重构。

---

## 0. 先说不动的

- **SQLite**：本地单用户、单进程写入、全库 4,155 行、热查询全部命中 `(user_id, id)` 索引的 Top-N 形态、无 `LIKE '%...%'` 全表扫描、WAL + NORMAL 已调优。增长 100 倍仍在舒适区。唯一重新考虑的触发点是 M7 跨端同步带来的多设备并发写——届时也不是"换掉"，而是在同步层/服务端选型（与 D8 拍板合并决策）。
- **Chroma/BGE-M3 向量库**、**Electron + FastAPI 壳**、**多人格 `user_id` 命名空间隔离**：量级与形态都匹配，需要的是纪律性检查（新表必须带 user_id 作用域），不是换机制。

---

## 1. 关键词记忆检索 —— 优先级最高，唯一"不做会悄悄伤害产品核心"的项

**现状**：线上跑的是 v1 旧版检索（`MEMORY_V2=0`）。`search_long_memory` / `search_long_memory_multi` 取该用户最近 500 条记忆，用中文字符二元组重叠打分；靠 LLM 把用户问题扩展成多个查询词来弥补召回，每轮多花数次检索；噪声靠调用方 TF-IDF 重排过滤。

**为什么它排第一**：召回质量就是产品灵魂——"某句话只有经历过这些事的她才会说"依赖的是"想得起"，不是功能数量。二元组匹配对措辞变化有硬上限（"上班摸鱼"查不到"昨天偷懒"），且 500 条窗口之外的长期记忆天然不可达。

**关键事实**：V2 记忆引擎（`backend/core/memory/engine.py`）**已经建好但默认关闭**；BGE-M3 权重惰性加载、向量化失败有"就绪后自动回填"机制。缺的不是地基，是把 V2 验证到能默认开启：老库向量重建的完整性校验、V2 与 v1 召回结果的 A/B 对比、性能（模型常驻内存）在 Electron 打包下的实测。

**建议动作**：作为 M1 剩余增量的最高优先级立项；验收 = 匿名化历史回放中 V2 召回不劣于 v1 + 资源占用可接受 + 默认开启后全量回归绿。

## 2. 主动消息的分散仲裁 —— 新增主动源之前必须先还的债

**现状**：主动候选源至少五个，各自维护去重键与空闲门槛：通用主动循环（`_proactive_key`）、问候、归档建议、约定跟进（`_PROMISE_FOLLOWUP_KEY`）、心事 Planner（`_PLANNER_KEY`）。仲裁逻辑按来源复制，历史上有过"poll_for 无锁导致并发重复生成"的真实事故。

**风险**：路线图八原则第 3 条要求"所有主动统一仲裁"；M5 惊喜编排、M7 世界事件每加一个源，"同一分钟说两件事/重复打扰"的风险就加一分。

**建议动作**：在 M5 剩余项（惊喜编排）开工前，先把**统一候选队列 + 单一仲裁器**立起来——所有源只产出候选（带优先级与最早可表达时间，`pending_thoughts` 已经是这个形态），由一处决定"现在发什么、发不发"。现有各源的 kv 去重键迁移为队列属性。

## 3. `activities` 通用活动壳 —— M3.4 开工前的必修课

**现状**：所有活动共用一张 `activities` 表 + kind 分叉。专注陪伴用了 `document_id=0` 哨兵列，共同目标刚加入，字段语义靠约定维持。路线图 M3 建议里自己写了"拆为 `backend/core/activities/` handler 架构；不要为每种活动复制一套生命周期表"。

**触发条件**：M3.4 共同创作（续写/世界观/歌单/观察日志）字段差异最大，开工时若继续往通用塞列，就是拆分信号到点的时刻。**建议动作**：handler 注册制（每种活动一个 handler，声明自己的字段映射与生命周期钩子），表结构保持通用壳 + 类型化 payload（`relationship_events.payload_json` 已有先例）。

## 4. `pipeline.process` 单体 —— 下一次横切改动痛到时拆

**现状**：1500+ 行、十几个编号阶段（3.0.1 / 3.0.2 / 4.1 … 5.11 / 6.1），所有上下文注入、状态更新、解释快照串在一处。本轮加"关系事件回忆"需要同时动上下文组装、注入点、解释快照三处；"config 必须局部导入"的铁律本身就是单体过大的症状。

**触发条件**：下一次横切改动（同时触及 ≥3 个阶段）导致回归成本明显升高时。**建议动作**：不必大重构，先做"阶段函数化 + 声明式注入清单"（每个阶段一个纯函数，签名是 ctx 进 ctx 出），pipeline 主干只剩编排。逐步迁移，每迁一个阶段跑一次全量回归。

## 5. 正则意图识别层 —— 意图面扩大时的统一切换点

**现状**：纠正检测（`is_correction`）、休息请求（`is_rest_request`）、搜索意图（`_needs_search`）、道别等全靠正则。零成本零延迟，误报控制也在精心维护（"不误伤调侃"）。

**触发条件**：可交互意图涨到七八种以上时。**建议动作**：统一为一次弱模型意图分类（每轮已有弱模型调用，边际成本小），正则降级为它的兜底；接受轻微延迟换取可扩展性。在此之前不动。

## 6. `kv_store` 杂物抽屉 —— 做选择性导出时顺手还

**现状**：张力、情绪记忆、各种主动去重键全是 JSON 塞在 kv_store。运行无碍，但 schema-less，没有清单。

**触发条件**：M1 剩余的**选择性导出/恢复**（E03）动工时。**建议动作**：给 kv 键建登记表（键名/归属模块/是否导出/是否敏感），导出器按清单枚举；不改变存储方式。

---

## 7. 建议排期（与路线图对齐）

| 顺序 | 事项 | 对应路线位置 | 触发条件 |
|---|---|---|---|
| 1 | MEMORY_V2 验证并默认开启 | M1 剩余增量 | 立即立项（唯一伤及核心体验的） |
| 2 | 主动统一仲裁器 | M5 剩余（惊喜编排）的前置 | 下一个主动源开工前 |
| 3 | activities handler 化 | M3.4 开工前 | M3.4 立项时 |
| 4 | pipeline 阶段函数化 | 横向质量轨道 | 下一次横切改动痛到时 |
| 5 | kv 键登记表 | M1 剩余（导出/恢复） | E03 动工时 |
| 6 | 意图分类统一切换 | 横向 | 意图数 ≥ 7~8 种 |

---

## 8. 维护说明

本文是评估快照，不是排期承诺。每完成一项或触发条件变化，更新对应条目状态；新部件出现时按同样格式追加（现状 / 触发条件 / 建议动作）。
