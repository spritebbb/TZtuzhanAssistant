## 1. D12：主动意愿 roll（最小，建议首做）

**目标**：现在「她要不要主动开口」= necessity ≥ 0.6 的确定性门（`expression_policy.NECESSITY_THRESHOLD`）。D12 在达标之后再加一层**概率化意愿**：necessity 回答「这事值得说吗」，willingness 回答「她此刻想不想说」——两个都过才出牌。

### 文件与接口
- `backend/core/expression_policy.py`：新增 `willingness(user_id, *, now=None) -> dict`（`{p, base, affection_term, suppression, roll, speak, hard_rule}`）与 `should_speak(user_id, score, *, hard_rule=False)`。
- `backend/core/config.py`：`WILLINGNESS_ENABLED`（flag 走 features）、`WILLINGNESS_BASE_{STAGE}`（初识 0.15 / 熟悉 0.30 / 亲密 0.45 / 恋人 0.55）、`WILLINGNESS_AFFECTION_WEIGHT=0.20`、`WILLINGNESS_TENSION_WEIGHT=0.30`、`WILLINGNESS_FOCUS_PENALTY=0.40`、`WILLINGNESS_FLOOR=0.05 / CEIL=0.95`。
- `tests/test_willingness_roll.py`。

### 公式与硬规则（ZZZChats §5 可搬点）
`p = base(stage) + (affection/100)×AFFECTION_WEIGHT − suppression`，suppression = `tension/100×TENSION_WEIGHT + 修复期标志×0.10 + 专注安静模式×FOCUS_PENALTY + 连续两轮未被回应×0.10`，clamp 到 [floor, ceil]。掷骰用 `random.Random(f"{user_id}:{source}:{minute}")` 的**可复现种子**——同一次机会重放结果一致，事后可解释。
**硬规则永不进骰子**（直接出牌，不掷）：用户点名/直接对话、约定到点跟进、确认与安全类投递、久别问候窗口——这些走既有 arbiter 路径，roll 只作用于通用主动与次级源（心事/归档建议/惊喜）。

### 可解释与护栏
- 解释快照（B5「为什么这样说」）追加一条：「这次主动：necessity 0.72 ✓ / 想说的概率 0.61，掷出 0.34 → 说了」或「→ 她这次没想说（roll 0.78）」；
- Q1 fixtures 加两个场景：硬规则路径永不被 roll 压制（点名必应）；roll 未中不得连续多日完全静默（连续 3 次未中后 p 临时 +0.15 的「想念补偿」）。

### 验收
`VERIFY: .venv/Scripts/python.exe -X utf8 tests/test_willingness_roll.py ;; .venv/Scripts/python.exe -X utf8 tests/test_proactive_arbiter.py ;; .venv/Scripts/python.exe -X utf8 tests/test_proactive_policy.py`

## 2. D10：成本护栏叙事化熔断

**目标**：接住 §17 的「实测 ¥30 上限」决策——到档不硬停、不弹系统提示，而是**她按日程去忙了**：非紧急主动降频→自主活动（批处理/离线叙事/惊喜）停发→极端档感知与批处理降级到弱模型。**用户主动发起的对话在任何档位都不受影响**（用户交互优先于自主活动，ZZZChats §8 保底规则）。

### 文件与接口
- `backend/core/cost_guard.py`（新）：`month_spend(user_id) -> float`（复用账本面板的定价换算，聚合当月 `usage_log`）；`tier(spend) -> "ok"|"soft"|"hard"|"extreme"`；`check(module: str) -> bool`（各消费方调用：`initiative`/`daily`/`offline`/`surprise`…，`chat` 永远 True）；`narrative_hint(user_id) -> str|None`（行为帧注入文案，每日至多一次）。
- `config.py`：`COST_MONTHLY_BUDGET_CNY=30.0`、`COST_SOFT_RATIO=0.70`、`COST_EXTREME_RATIO=1.30`、`COST_NARRATIVE_ENABLED=1`。
- `kv_registry.py` 登记 `cost:{user_id}`（当月缓存值+档位+提示日；可由 usage_log 重算 → 不进关系包导出）。
- 接线三处：`initiative._arbited_proactive` 出牌前 `check("initiative")`（soft 档同时把 necessity 阈值 +0.15）；`daily` 批处理各 LLM 步前 `check("daily")`（跳过时 journal 记原因、不产半成品）；`model_routes` 在 extreme 档把 perception/batch 路由降级到廉价模型。

### 档位语义表
| 档 | 触发 | 她的行为（叙事面） | 工程面 |
|---|---|---|---|
| ok | <70% | 正常 | — |
| soft | ≥70% | 偶尔提一句最近事多（行为帧，≤1 次/天） | 非紧急主动 necessity 阈值 +0.15 |
| hard | ≥100% | 自主的事「排到下个月再做」，不提数字 | initiative/daily/offline/surprise 的 LLM 全停；用户聊天照常 |
| extreme | ≥130% | 同上+回复稍简短（texture 注入） | 感知与批处理降级弱模型；用户聊天仍不拒答 |

### 验收
`VERIFY: .venv/Scripts/python.exe -X utf8 tests/test_cost_guard.py ;; .venv/Scripts/python.exe -X utf8 tests/test_daily_trigger.py ;; .venv/Scripts/python.exe -X utf8 tests/test_surprise.py`
覆盖：档位换算/跳过不产半成品/用户聊天永不被拦/提示每日一次/kv 登记齐全/extreme 模型降级/自己也被记账。

## 3. D9：局势档案（恒定世界快照层）

**目标**：给「当前世界」一个 ≤2.5k tokens 的滚动快照，**每轮恒定在场**（不靠检索命中）——活跃钩子（G03 悬念、未兑现约定、进行中的目标）永不怕漏召；上下文组装 O(1)。历史「活在状态里」而不是逐字对话里。

### 数据模型（schema v43）
```sql
CREATE TABLE situation_files (
  user_id TEXT PRIMARY KEY,
  format_version INTEGER NOT NULL,
  state_json TEXT NOT NULL,          -- 见下，冻结排序 ensure_ascii=False
  char_budget INTEGER NOT NULL,      -- 默认 5000（≈2.5k tokens CJK）
  last_event_id INTEGER,             -- 已吸收到哪个 relationship_event
  turn_count INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL,
  recompiled_at TEXT                 -- 上次全量重编译（防漂移兜底）
);
```
reset 双清单登记；**不进关系包导出**（派生态，恢复后由 daily 重编译重建）。

`state_json` 六节（全部来自真实持久数据，LLM 只做压缩不改事实）：
1. 活跃目标（goals 进行中：动机+下一步）
2. 未兑现约定（promises pending，含到期日）
3. 悬念与开放问题（open_questions active）
4. 近期关键事件（relationship_events 近 7 条保留细节 + 更早 ≤3 条压缩为一行）
5. 当前生活与场景（presence/季节/心情档/精力，来自 schedule+state）
6. 关系焦点（最近 7 天双视角/修复/里程碑各 ≤1 条引用）

### 调用链
- **增量更新**（`situation.update_after_turn`，挂在 `turn_effects`）：仅当本轮产生 relationship_event/artifact/promise/open_question 变化，或累计 10 轮未更新，或会话归档时触发；输入=旧 state_json+本轮变化摘要 → LLM（task=batch_other，温度 0.2，JSON 硬 schema）→ 校验通过才落库，失败保旧文件绝不阻塞聊天；
- **防漂移重编译**（`situation.recompile`，挂 `daily.py` 批处理，受 D10 `check("daily")` 门控）：从 SQLite 权威数据全量重建，替换 LLM 累积态；effect_ledger 记录重编译差异节数；
- **注入**（`turn_context_gather`）：人格之后、记忆召回之前，一条独立 system「局势档案」；与 context_registry 共享注入预算（它不是 registry 条目，是常驻层）；
- **解释露出**：解释快照新增「局势档案」来源条目；`GET /api/situation` 供 debug（脱敏后同款 JSON）。

### 失败与安全
增量更新任何失败=保旧；重编译失败=保旧+effect_ledger 记失败；档案内容只引用既有事件摘要，不引入用户新原文；`situation_enabled` flag 关闭时整层静默退场（管线零改动语义不变）。

## 4. D11：离线补算管线（依赖 D9+D10）

**目标**：应用关着的这段时间，她的日子照「过」——重开时按行程模板补算这段世界发生了什么，护栏限额裁剪后带离线时间戳批量入库，再**排队回放**（「正在输入」逐条展示、可跳过）。是 P2-06 重逢三段式的工程管线化。

### 文件与接口
- `backend/core/offline_recap.py`（新）：`plan(user_id, from_ts, to_ts) -> dict`（重放 schedule 周模板得候选生活事件，纯确定性不调 LLM）；`generate(user_id, plan) -> RecapResult`（≤2 次 LLM：事件筛选与措辞；D10 hard 档=0 次纯确定性罗列）；`trim(plan, cap=8)`（超出降级为一条摘要行）。
- schema v43 同批：`offline_recaps(user_id, from_ts, to_ts, events_json, state, delivered_at, skipped_at)`；补算落成的生活在 `character_life_events` 记 `kind='offline:…'` 派生行（与真实 tick 行区分，导出时随 life 类走）。
- 回放：复用 `enqueue_proactive` 新 source=`offline_recap`，逐条投递；前端 ChatView 对该 source 显示「（那时）」时间戳与跳过按钮，跳过=剩余条目折叠成最后一条摘要。
- 触发：解锁后首次就绪（reunion 判定之后、问候之前），与 P2-06 的「预谋惊喜」不抢额度（offline_recap 不占每日主动额度，走自己的 cap）。

### 边界
离线 >48h 只按日采样；LLM 失败退确定性日程罗列（诚实不编造）；任何情况下不回溯修改既有事实表（只新增派生行）；`offline_recap_enabled` flag。
